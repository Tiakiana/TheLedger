# Project: The Ledger — Multiplayer Inventory Management System

## Your task

Build a complete, functional, responsive web application called **The Ledger**.

The Ledger is a server-authoritative inventory and asset transfer system designed for multiplayer roleplaying games.

It is NOT a game engine. Do not introduce combat, character statistics, quests, crafting, movement, maps, or other gameplay systems unless explicitly requested.

The system exists to let a Gamemaster (GM) manage players, roles, inventory items, currencies, and asset ownership, while allowing players to organize inventories and donate assets to other roles.

**The server is the absolute single source of truth.** The browser must never be trusted to determine ownership, quantities, transfer results, or permissions.

Build the application using React and TypeScript, with a persistent server-side database and a real backend.

The completed application must work in modern desktop and mobile browsers.

---

# 1. Fundamental concepts

## Players
- Each player has an individual account with a username and password issued by the GM.
- Each player may be assigned to at most one role at a time.
- Multiple players may share the same role.
- Players assigned to the same role share exactly the same inventory.
- Every action must be attributable to the individual player who performed it.

## Roles
- A role is an identity within the game, such as a character, noble house, kingdom, organization, or faction.
- Each role has exactly one inventory.
- Roles exist independently of player accounts.
- The GM may create, rename, duplicate, delete, and assign roles.
- A role may have zero, one, or multiple players assigned.
- Unassigned players may log in but cannot perform inventory actions until assigned.

## Inventories
- Every role owns its own persistent inventory.
- The inventory may contain stackable items, unique items, and currency balances.
- Inventories have no fixed capacity.
- Inventory ownership and contents are stored on the server.

# 2. Inventory interface

Create a visually clean, intuitive inventory interface.

### Grid
- Use a grid layout displaying approximately five columns and five rows on a typical desktop viewport.
- The inventory must support an unlimited number of items through virtualized or incremental scrolling.
- Adapt the number of columns automatically to narrower screens.
- Show an item image or placeholder, item name, and stack quantity.
- For example, five bricks should appear as one item with a visible "×5" overlay.
- Unique items must be displayed individually.
- Allow users to click or tap an item to inspect its details.

### Organization
- Allow users to rearrange items manually using drag-and-drop.
- Make manual arrangement persistent and shared by all players controlling that role.
- Provide sorting by:
  - Name, ascending and descending
  - Quantity, ascending and descending
  - Most recently acquired
  - Least recently acquired
  - Custom manual order
- Automatic sorting must not destroy the saved custom arrangement.
- Display a clear indication of the active sorting mode.

### Responsive behavior
- Desktop: full grid and drag-and-drop functionality.
- Mobile: smaller responsive grid with touch-friendly controls.
- Provide a tap-based method for moving and selecting items so mobile users are not dependent on drag-and-drop.
- Avoid horizontal overflow.

# 3. Items

The GM can create reusable item definitions.

Each definition contains:
- Unique internal ID
- Name
- Description
- Optional image
- Stackable or unique designation

### Stackable items
- Identical definitions combine into a stack.
- The quantity must be a positive integer.
- Quantities decrease and increase through authorized server operations.
- Removing the final unit removes the stack from the displayed inventory.

### Unique items
- Each unique item has its own internal instance ID.
- Unique items cannot stack.
- Multiple unique instances may use the same definition.
- Unique items can be donated, moved, created, or deleted by the GM.

### Land deeds
- Deeds are ordinary inventory items, not a separate land-management system.
- They may be implemented as unique items named after the relevant property.
- Their ownership is represented by the role that possesses the item.
- Do not introduce geographical mapping, property databases, or legal ownership logic.

# 4. Currencies and abstract resources

The GM may define an unlimited number of currencies or resources.

Examples include:
- Money
- Gold
- Political power
- Influence
- Prestige

Each currency definition contains:
- Unique ID
- Name
- Optional icon
- Integer or decimal precision
- Optional minimum and maximum
- Optional visual gauge configuration

### Interface
- Display resource balances separately from regular inventory item cards.
- Every currency displays a numerical amount.
- Optionally display a gauge or dial indicating its value relative to its configured range.
- Where no maximum exists, display a numerical balance without implying a full or empty gauge.
- Provide a donation control for each currency.
- Players cannot directly edit their balances.
- The GM may create, adjust, subtract, reset, or delete currency balances.

Currency transfers must use exact numeric calculations, avoiding floating-point rounding errors.

# 5. Donation system

There must be a prominent, easily accessible **Donate** button.

Players may donate items or currencies to another role.

Implement two distinct donation workflows.

## Workflow A: Item-first donation

1. The player finds an item or currency.
2. The player selects Donate.
3. A donation interface opens.
4. The player chooses a recipient role.
5. The player chooses the amount to donate.
6. The server validates ownership and available quantity.
7. The player confirms the donation.
8. The server reserves the selected assets.
9. A visible five-second cancellation countdown begins.
10. If the sender cancels before the deadline, the reservation is released.
11. Otherwise, proceed according to the server's recipient-approval setting.

The countdown must:
- Be clearly visible.
- Use a small circular timer or dial.
- Display the remaining seconds.
- Include an obvious Cancel button.
- Continue to be enforced by the server even if the browser disconnects.

## Workflow B: Recipient-first donation

1. The player selects Donate.
2. The player searches for a recipient role by name.
3. The player selects the role.
4. A donation composition interface appears.
5. The player can drag multiple items into the donation area.
6. The player can also add items using tap/click controls.
7. The player specifies quantities for stackable items and currencies.
8. The interface shows everything being donated.
9. The player confirms the donation.
10. The server reserves all included assets in one atomic operation.
11. The player gets the same five-second cancellation opportunity.
12. The donation then proceeds according to the approval setting.

A multi-item donation must be treated as one transaction. It must not partially succeed.

## Donation rules

- Donations go to roles, not individual player accounts.
- A role cannot donate to itself.
- A player cannot donate more than the role owns.
- Reserved assets cannot be included in another donation.
- Each donation receives a unique transaction ID.
- The server timestamps and authorizes every operation.
- Concurrent requests must not allow duplication or negative balances.
- The frontend must reflect actual server state.

## Recipient approval

The GM can enable or disable mandatory donation acceptance at the server level.

When approval is disabled:
- Donations finalize automatically after the cancellation period.

When approval is enabled:
- The donation enters a pending state after the cancellation period.
- Any authorized player controlling the recipient role may accept or reject it.
- Acceptance completes the transfer.
- Rejection releases the reserved assets to the sender.
- Multiple players must not be able to resolve the same donation twice.

Provide a recipient inbox for pending donations.

Use server-side deadlines and transaction state transitions, not browser timers, as the authoritative mechanism.

# 6. Gamemaster dashboard

Create a dedicated GM interface.

The GM has unrestricted administrative control over the inventory system.

### Player management
- Create player accounts.
- Issue and reset account passwords.
- Search players by username.
- Assign or unassign roles.
- View which players control each role.
- Disable player accounts when required.

### Role management
- Create roles.
- Rename roles.
- Search and browse roles.
- Assign multiple players to one role.
- Duplicate roles.
- Delete roles with explicit confirmation.
- Open and edit any role's inventory.

### Role duplication

When duplicating a role:
- Create a new independent role.
- Copy its name with a distinguishable default suffix.
- Duplicate all inventory contents and quantities.
- Duplicate all currency balances.
- Duplicate the inventory's custom arrangement.
- Create new item-instance IDs for every copied unique item.
- Do not automatically copy player assignments.
- Do not alter the original role.

### Item management
- Create, edit, and delete item definitions.
- Upload or select item images.
- Add items to any role inventory.
- Remove items from any inventory.
- Change stack quantities.
- Move items between role inventories.
- Create and remove unique item instances.

### Currency management
- Define new currencies.
- Edit currency settings.
- Adjust balances for any role.
- Transfer currency between roles.
- View currency balances across roles.

### Transactions and administration
- Inspect the complete transaction history.
- Filter history by player, role, asset, action type, and date.
- Distinguish donations from direct GM operations.
- Inspect cancelled, pending, rejected, and completed donations.
- Record GM actions in the same audit system.
- Prevent editing or deleting existing audit records through the normal application interface.

The transaction history must be accessible only to the GM.

Players may see their own current balances and pending donation states, but must not have access to the permanent audit history.

# 7. Server architecture

Use a genuine server-authoritative architecture.

Recommended technologies:
- React with TypeScript
- Vite for the frontend
- Node.js with TypeScript for the backend
- Fastify or Express for the API
- PostgreSQL for online hosting
- SQLite as a supported local deployment option
- Prisma or another migration-capable database layer
- WebSockets for live updates

You may suggest alternatives if they materially improve reliability or deployment simplicity.

### Required backend responsibilities
- Authenticate accounts.
- Authorize every operation.
- Enforce player-role assignments.
- Store all item and currency ownership.
- Validate and execute transactions.
- Reserve assets during pending donations.
- Enforce donation cancellation deadlines.
- Process acceptance and rejection.
- Manage all GM operations.
- Write permanent audit records.
- Broadcast relevant changes to connected clients.

The server must never trust client-submitted quantities, permissions, timestamps, or ownership claims.

### Shared inventories

When multiple players control the same role:
- All clients receive live inventory updates.
- A change performed by one player appears for the others.
- Conflicting operations are resolved on the server.
- Shared roles must never lead to duplicate item transfers.

- The application can operate without an internet connection once dependencies and assets are installed.

## Online mode

Local and online deployments are independent installations. Do not build automatic synchronization between them.

Provide instructions for both deployment options.

## Finalized donation and inventory rules — v1.1

### Recipient approval deadline

If recipient approval is enabled, the system must provide a **five-minute approval window**, beginning immediately after the sender's five-second cancellation window expires.

- The recipient role's players receive a real-time pending donation notification.
- The donation appears in the recipient's pending donations inbox.
- Display a countdown indicating the remaining approval time.
- Any authorized player assigned to the recipient role can accept or reject the donation.
- If accepted before the deadline, the server atomically transfers all reserved assets.
- If rejected, the server releases all reserved assets to the sending role.
- If no action is taken within five minutes, the server automatically rejects the donation and releases all reserved assets.
- Assets remain reserved throughout both countdown periods.
- Once resolved, a donation cannot be accepted, rejected, or cancelled again.
- Timers are server-authoritative and must survive browser disconnections and server restarts.
- The server must ensure that approval arriving after the deadline cannot complete the transfer.

### Role duplication

Duplicating a role creates an exact independent copy of its inventory, including all stackable items, unique items, currency balances, and saved custom ordering.

Every duplicated unique item receives a new internal instance ID, while retaining the original item's visible properties.

Player assignments and pending transactions are not duplicated.

### Persistent sorting

The custom item layout is stored persistently for each role. Automatic sorts by name, quantity, or acquisition recency are temporary display modes and never overwrite the custom layout.

### Shared-role concurrency

All players assigned to the same role share one authoritative inventory and receive real-time updates.

Every server operation must be transactional, preventing conflicting donations, double spending, item duplication, and inconsistent balances.

### Default approval configuration

The GM controls a single server-wide setting determining whether recipient approval is required. Automatic acceptance is the default.
